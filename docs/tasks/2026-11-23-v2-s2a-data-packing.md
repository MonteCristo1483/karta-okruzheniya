# Задача V2-S2a: упаковка данных и замеры

Дата: 2026-11-23. Исполнитель: pipeline-исполнитель (механика).
Полоса: `pipeline/` и `config/`. **`web/` не трогать, деплой не менять.**

## Контекст

Шаг 1 (#160) закрыт: район — параметр, `is_home` работает, три района
собраны. Замеры на 125 районов: 149–212 тыс. жилых домов, PMTiles зданий
131–179 МБ, **индекс 16 МБ** (нельзя грузить), **geojson 263–346 МБ**
(нельзя публиковать), маршрутов ~745 тыс. (≈640 МБ JSON).

Цель шага — не «сделать красиво», а **снять формат поставки**, при котором
город влезает в GitHub Pages: данные ≤400 МБ, файлов тысячи, а не сотни
тысяч, первый экран не растёт.

## Что сделать (четыре артефакта)

### 1. Шардированные пакеты маршрутов и изохрон

Сейчас: `routes/<building_id>.json` + `isochrones/<building_id>.json`
(6 612 файлов на Пресню, ~400 тыс. на город).

Новый формат: `routes/<district_id>/<shard>.json.gz` и
`isochrones/<district_id>/<shard>.json.gz`, где `shard = building_id % 16`.
Внутри — объект `{ "<building_id>": <содержимое старого файла>, ... }`,
сжатый gzip. 16 шардов на слой на район дают ~4 000 файлов на город.

Скрипт `pipeline/pack_district.py --district <id>`:
- читает существующие файлы маршрутов/изохрон района, **не пересчитывает**;
- пишет шарды; порог каждого шарда — не больше ~1 МБ gzip, иначе шардов
  больше (шаг кратности фиксированный, размер — информативный);
- проверка чтения: взять 20 случайных id, собрать их payload обратно и
  сравнить с исходным файлом побайтово/по содержимому.

Для Пресни маршруты есть — упаковать **только жилые** (`is_home`), исходные
файлы не удалять. У Тверского и Арбата маршрутов нет — для них измерить
только формат на пустом наборе и отметить это в отчёте.

### 2. Компактный индекс

Сейчас `buildings-index.json` — 188 КБ на 1 696 жилых (≈16 МБ на город).

`pipeline/build_index.py`: один файл `index.json.gz` с **колоночной**
структурой вместо массива объектов:

```json
{"v":1,"ids":[...],"lon":[...],"lat":[...],"addr":[...]}
```

- только жилые дома; `lon/lat` — 6 знаков; `addr` — «улица, дом»;
- цели: **≤3 МБ gzip на 150 тыс. домов**, разбор ≤200 мс в браузере;
- проверка: контрольная выборка 50 адресов находит тот же id, что и старый
  индекс (сравнение делается по трём районам).

Кастомный бинарный формат не нужен — сначала пробуем колоночный gzip JSON.

### 3. Подложка в PMTiles

`basemap.geojson` Пресни 1,32 МБ; на город ~150–250 МБ. Добавить сборку
PMTiles (tippecanoe уже есть в `pipeline/docker`, версия 2.79.0) для bbox
трёх районов: `pipeline/build_basemap.py --pmtiles` или отдельный скрипт.
Слои/классы/подписи не менять. Замер: размер PMTiles против geojson.

### 4. Манифест районов

`data/districts/manifest.json`: для каждого района `id`, `name`, `bbox`,
список файлов с размером и sha256 (здания, индекс, маршруты, изохроны,
подложка). Манифест — то, чем потом будет жить фронтенд и деплой.

## Критерий приёмки

1. Шарды Пресни: число файлов, суммарный размер gzip, round-trip 20/20
   совпадений; исходные `routes/` не изменены.
2. Индекс: фактический размер gzip и экстраполяция на 150 тыс. домов;
   **цель ≤3 МБ**. Если не влезает — стоп и отчёт с причиной (не «сожмём
   потом»).
3. Подложка: размер PMTiles для трёх районов, экстраполяция на город.
4. Манифест валиден: все файлы на месте, sha256 сходятся.
5. 60 тестов зелёные; `web/` и `config/scoring.json` без диффа.
6. Итоговая таблица «что на город»: индекс, подложка, маршруты, изохроны,
   здания — сумма и запас до 400 МБ.

## Стоп-условия

- Индекс не влезает в 3 МБ после колоночного gzip — стоп, отчёт с числами.
- Нужны изменения в `web/` или деплое — стоп (это шаг 2b).
- Больше 8 изменённых файлов или 90 минут — стоп и отчёт.
