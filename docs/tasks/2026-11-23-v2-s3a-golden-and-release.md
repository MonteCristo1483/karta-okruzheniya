# Задача V2-S3a: golden на жилых + доставка данных через Release

Дата: 2026-11-23. **Модель: DeepSeek V4.1 Flash (`opencode-go/deepseek-v4.1-flash`).**
Полоса: `pipeline/`, `.github/workflows/deploy.yml`, `docs/DATA_RELEASE.md`.
**`web/`, `config/`, ветку `data` не трогать.**

## Контекст

После перехода на `is_home` (шаг 2c) из 18 golden-фактов проверяются только
7: остальные 11 указывают на здания, которые теперь нежилые. Файл не
потерян, но защита от регресса ослабла втрое — перед полным прогоном это
недопустимо.

Второе: полный прогон даст архив ~380 МБ, а git-блоб ограничен 100 МБ.
Ветка `data` для такого архива не годится.

## 1. Golden на жилых

`pipeline/build_golden.py` сейчас выбирает дома района без учёта `is_home`.
Добавить фильтр `is_home` в выборку и пересобрать набор:

- **18 фактов**, все — жилые дома; сохранить тот же набор факторов
  (вход метро/транспорт, порог магистрали, стройка, дальность), что и было;
- значения берутся из внешних источников и формулы, как сейчас, — **не
  копировать вывод скоринга** (иначе тест проверяет сам себя);
- допуски, `config/scoring.json` и веса не менять;
- проверка: `check_golden.py` даёт 18/18, в отчёте — id и адреса.

Если после фильтрации не хватает жилых домов под какой-то фактор — выбрать
жилой дом с тем же фактором в том же районе, записать это в отчёт. Не
подменять фактор на другой.

## 2. Доставка через Release

`deploy.yml` сейчас берёт `data.zip` только из ветки `data`. Сделать:

1. Приоритет: ассет `data.zip` из GitHub Release с тегом `data`
   (`gh release download data --pattern data.zip -O ... --clobber`).
2. Если релиза нет — падать обратно на ветку `data` (текущий путь), не
   ломая деплой.
3. Валидация и `check_golden` — как сейчас, до сборки сайта.
4. Вход workflow `data_ref` сохранить; добавить `data_tag` (по умолчанию `data`).

Обновить `docs/DATA_RELEASE.md`: как выпускать данные (собрать zip →
создать/обновить релиз с тегом `data` → запустить Deploy), как откатиться
(предыдущий релиз/коммит ветки).

Ручная загрузка ассета — ожидаемая, один раз на выпуск данных. Автоматическую
загрузку не изобретать: локального `gh` нет.

## 3. Предупреждения валидатора

После перехода валидатор даёт ~15 некритичных предупреждений. Выписать их
категориями (например: отсутствующий год, POI без классификации, расстояние
на границе допуска), отметить, какие из них — блокер для полного прогона.
**Ничего не «чинить» молча**: только список и классификация в отчёте.

## Что нельзя

- Менять `config/scoring.json`, `config/buildings.json`, `is_home`.
- Трогать `web/`, карточку, материалы, формат данных.
- Запускать полный прогон, считать маршруты, менять ветку `data`.
- Добавлять зависимости. Коммитить данные.

## Проверка

```powershell
pipeline/.venv/Scripts/python.exe pipeline/build_golden.py
pipeline/.venv/Scripts/python.exe pipeline/check_golden.py <распакованные данные>
pipeline/.venv/Scripts/python.exe -m unittest discover -s pipeline -p "test_*.py" -v
git diff --stat
```

Плюс сухая проверка деплоя: если владелец успел создать релиз с тегом
`data`, скачать ассет командой из workflow и сверить sha256/размер; если
релиза нет — записать в отчёт точную команду для проверки после загрузки.

## Критерий приёмки

1. Golden: 18 фактов, все жилые, 18/18 проходят; допуски и скоринг не
   изменены.
2. Deploy: при отсутствии релиза работает по-старому (ветка), при наличии —
   берёт ассет; обе ветки кода покрыты понятной ошибкой при сбое.
3. 64+ тестов зелёные; `web/` и `config/` без диффа.
4. Список предупреждений валидатора с классификацией.
5. `docs/DATA_RELEASE.md` обновлён.

## Стоп-условия

- Для 18 жилых фактов не хватает исходных данных — стоп с отчётом, не
  ослаблять допуски.
- Приходится трогать `web/` или скоринг — стоп.
- Больше 8 файлов или 90 минут — стоп.

## Отчёт (≤40 строк)

1. PR, commit, diffstat.
2. Golden: 18/18, список id/адресов, что изменилось в выборке.
3. Deploy: как проверена ветка «релиз есть» и «релиза нет».
4. Предупреждения: категории и что из них блокер.
5. Риски одной строкой.
