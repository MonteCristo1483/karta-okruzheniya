# Задача P1: POI как слой карты, а не DOM-маркеры

Дата: 2026-11-24. **Модель: DeepSeek V4.1 Flash (`opencode-go/deepseek-v4.1-flash`).**
Полоса: `web/app/map.tsx`, `web/app/icons.ts` (если нужно). Данные, пайплайн,
карточку и скоринг не трогать.

## Контекст

Прод тормозит, и главная причина — не здания, а POI. Владелец проверил:
с выключенными слоями POI телефон приемлем, с 1–2 включёнными — катастрофа.

Причины в коде:
- при старте скачиваются `poi.geojson` **всех 132 районов** и сливаются в один
  FeatureCollection (~15 тыс. точек);
- каждая точка в кадре создаётся как `new maplibregl.Marker(...)` — **DOM-узел**
  с обработчиком; подписи — тоже отдельные DOM-маркеры;
- при движении карты всё это пересоздаётся/перепозиционируется.

## Цель

POI рисуются **одним symbol-слоем** (или несколькими по категориям), а не
DOM-маркерами; грузятся только видимые районы; на обзоре показываются не все
категории. Внешний вид на рабочем зуме (15–16.6) сохраняется.

## Что сделать

1. **Слой вместо DOM.** Источник — GeoJSON с POI видимых районов. Один слой
   `poi` типа `symbol` (или по одному на категорию) с `icon-image` из
   существующих иконок `icons.ts` (зарегистрировать через `map.addImage`) и
   `text-field` из `name`. Клик по слою → та же логика выбора POI, что сейчас.
   Все `new maplibregl.Marker` для POI и подписей убрать.
2. **Загрузка по видимым районам.** На `moveend` (с дебаунсом) определять
   районы по bbox из манифеста, догружать недостающие `poi.geojson` (кэш в
   памяти), из источника оставлять только видимые (+1 соседний) районы.
   На старте — не больше 3–4 районов, а не 132.
3. **Плотность по зуму** (правило продукта, фиксируем):
   - z < 11 — POI не показываем вообще;
   - z 11–12 — только метро и ж/д платформы;
   - z 12–13 — + парки;
   - z 13–14 — + школы и сады;
   - z ≥ 15 — + магазины;
   - подписи (`text-field`) — только с z ≥ 14, ниже только иконки;
   - при z < 14 включить `icon-allow-overlap: false`, чтобы не рисовать
     тысячи наложенных иконок.
4. **Деревья** (circle-слой, до 7 500 точек) не трогать в этой задаче, но
   проверить, что после замены POI они не стали узким местом; если да —
   отдельная задача.

## Что нельзя

- Менять карточку, скоринг, данные, формат данных, пайплайн, тайлы.
- Менять внешний вид POI на рабочем зуме (цвета, иконки, размеры) — паритет.
- Добавлять зависимости и серверные функции.
- Убирать клик по POI или ломать выбор дома.

## Проверка

```powershell
cd web
node node_modules\typescript\bin\tsc --noEmit -p tsconfig.json
npm run build
npm run e2e
```

Ручная проверка на собранном `dist` (или проде после деплоя):
- в DOM нет сотен `.maplibregl-marker` (ожидаемо: 0 для POI);
- на z10–12 при всех включённых слоях карта двигается плавно, в кадре
  только метро (z11–12);
- на z15–16.6 POI и подписи выглядят как раньше, клик открывает то же;
- переключение слоёв не вызывает повторной загрузки всех 132 файлов;
- сетевой лог: на старте ≤ 4 запросов `poi.geojson`, при движении — только
  новые районы.

## Критерий приёмки

1. `document.querySelectorAll('.maplibregl-marker').length` не растёт с числом
   POI (0 для POI-маркеров).
2. z10–12 с включёнными слоями — плавно на десктопе; на телефоне без
   «катастрофы» (субъективно владельца).
3. z15–16.6 — визуальный паритет с текущим (скрин до/после, 2 кадра DPR 1).
4. Клик по POI и выбор дома работают; `tsc`, build, e2e зелёные.
5. Дифф только в `web/`.

## Стоп-условия

- Без DOM-маркеров ломается клик/подписи и починить за 30 минут нельзя —
  стоп, отчёт с вариантами.
- Нужны новые данные/пайплайн — стоп (это отдельный шаг).
- 90 минут — стоп с отчётом.
