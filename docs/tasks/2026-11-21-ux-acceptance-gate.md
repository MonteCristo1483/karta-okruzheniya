# Задача P1: остановить auto-merge UX до приёмки владельцем

**Рекомендуемая модель:** GPT-6 Luna (workflow/security design).
**Исполнитель:** одна сессия; сначала бриф должен попасть в `origin/main`.
**Bootstrap:** владелец подтвердил включение Code Owner review для `main`
21.11.2026; `.github/CODEOWNERS` опубликован.

## Обязательный bootstrap-предохранитель

До передачи кода исполнителю владелец включает для `main` GitHub rule:
PR required, Code Owner approval required, stale approvals dismissed и no
bypass. CODEOWNERS — `/.github/CODEOWNERS`; точные действия владельца —
`docs/tasks/2026-11-21-owner-enable-codeowners.md`.

Если это правило не активно, задача **только read-only design**: не пушить
изменённый workflow под текущим Autopilot, который выполняется из push-ветки
с write permissions и может сам изменить свой gate.

## Проблема

`.github/workflows/autopilot.yml` после push запускает тесты, открывает PR,
автоматически мержит его и вызывает Deploy. Скриншоты и ревью хаба/владельца
сейчас происходят после merge. UX-визуальные изменения могут попасть на
production без предварительной приёмки.

## Цель

Для PR, затрагивающих продуктовый UI/карту (`web/**`), сохранить тесты и
создание PR, но запретить merge и Deploy до явного owner approval. Не менять
поведение auto-merge для не-UX задач без необходимости.

## Требования

1. UX PR после зелёных тестов остаётся открытым; отсутствие approval никогда
   не приводит к merge или Deploy.
2. Владелец подтверждает кадры/сценарий явным approval (label `ux-approved`
   либо безопасный эквивалент, описанный в отчёте). Только после него
   запускается доверенный путь merge/deploy.
3. Перед merge проверяется, что тесты относятся к текущему HEAD PR; push новых
   коммитов сбрасывает ранее полученное approval или требует нового подтверждения.
4. Негативный путь проверен: без label / при красных тестах merge и Deploy
   не запускаются. Позитивный путь проверен без отдельного production-PR.
5. Не выполнять код PR с write-token в недоверенном контексте. Не добавлять
   небезопасный `pull_request_target` с checkout/исполнением кода PR. Минимизировать
   permissions, сохранять pinning Actions по SHA.
6. Если часть защиты требует изменения GitHub rules/settings вне репозитория,
   перечислить конкретный шаг владельцу; не логиниться под его аккаунтом.

## Нельзя

- Не менять `web/`, данные, `config/scoring.json`, `main` или `gh-pages`.
- Не обходить тесты и не делать ручной merge/deploy.
- Не блокировать обычные docs-only задачи без обоснования.

## Проверки и критерий приёмки

- Тесты workflow/классификатора путей подтверждают: `web/**` требует label;
  без label нет merge/deploy; approval после успешных тестов разрешает merge.
- Не-UX branch сохраняет ожидаемый текущий цикл.
- Workflow lint/проверки и существующий CI зелёные.
- В отчёте указаны PR/run IDs для обоих сценариев; тестовый UX-путь не
  публиковал код приложения в production.
