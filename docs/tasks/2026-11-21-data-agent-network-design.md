# Задача: спроектировать онлайн-сетку data-агентов

**Режим:** архитектурный отчёт, read-only. Код и данные не менять.
**Рекомендуемая модель:** GPT-6 Luna.
**Статус:** схема подготовлена хабом 21.11.2026:
`docs/research/data-agent-network-design.md`.

## Контекст

- Владелец разрешил максимально собирать данные из публичных открытых API.
- Полевой проверки не будет; нужное качество достигается версиями источников,
  provenance, валидацией, покрытием и онлайн-сверками.
- Инвентаризация источников: `docs/research/data-source-inventory-2026-11-21.md`.
- Проект: один район, Пресня; 3 306 зданий; формула строго в
  `config/scoring.json`; новые данные не должны менять scoring автоматически.

## Цель

Предложить минимальную и управляемую одним владельцем схему агентов, которая
регулярно обнаруживает обновления открытых источников, получает их через API,
нормализует, проверяет и готовит отчёт/кандидатный экспорт без автономной
публикации непроверенных данных.

## Что описать

1. Роли: каталогизатор источников, коннекторы по доменам, нормализатор,
   QA покрытия/геометрии, координатор релиза. Указать, какие роли должны
   быть агентами, а какие — обычным детерминированным кодом.
2. Контракт данных/provenance: source ID и версия, время получения,
   лицензия/атрибуция, геометрия и точность, confidence, coverage, исходный ID.
3. Автоматический цикл: проверка версии/свежести → загрузка с лимитами и
   повторами → staging → дедупликация и валидация → отчёт изменений →
   существующий release flow.
4. Стоп-условия: неизвестные условия источника, неверная схема, битая
   геометрия, резкое падение покрытия, дубли, расхождение независимых
   источников. Предложить безопасный откат и воспроизводимость выгрузки.
5. Приоритеты для первого подключения по одному: data.mos.ru 2855 (ордера),
   60661 (остановки), затем пробелы садов/магазинов/промышленных объектов.
   Не считать кандидата одобренным только из-за доступности endpoint.
6. Оценку затрат для соло-разработчика: сколько специализированных ролей
   нужно реально, как ограничить токены/повторы и как агент сообщает о
   блокере вместо бесконечного поиска.

## Ограничения

- Не менять код, данные, `config/scoring.json`, схему индекса или текущую
  формулу.
- Не использовать секреты в промптах и логах; не обращаться под аккаунтом
  владельца; учитывать индивидуальные API-ключи и rate limits.
- Не обходить лицензии, авторизацию и ограничения источников.
- Не генерировать отсутствующие геометрии и не выдавать оценку модели за факт.
- Не предлагать агентам прямой push в `data`, `main` или `gh-pages`.

## Критерий приёмки

Короткая схема потока, контракты входов/выходов агентов, точки человеческого
контроля, список автоматических проверок и приоритет следующей одной
реализационной задачи. Все предположения и незакрытые условия явно помечены.
