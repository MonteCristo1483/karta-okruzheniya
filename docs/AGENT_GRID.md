# Агентная сетка и онлайн-фабрика

Документ для соло-проекта: как работать с несколькими агентами, не получить
конфликты в файлах и не превратить ноутбук в единственную точку отказа.

## 1. Роли

| Роль | Где работает | Что можно | Что нельзя |
|---|---|---|---|
| **Диспетчер** (главная сессия) | корень репозитория | приоритеты, review diff, тесты, merge, deploy | писать большие куски кода |
| **Pipeline** | `C:\Users\starg\karta-pipeline` (worktree) | `pipeline/`, `config/`, `data/`, `docs/` | `web/`, push в `main`/`gh-pages`, deploy |
| **Web** | `C:\Users\starg\karta-web` (worktree) | `web/` | `pipeline/`, `config/`, `data/`, push в `main`/`gh-pages`, deploy |
| **Researcher** | subagent из диспетчера | читать, искать, webfetch | править файлы, запускать shell |
| **Reviewer** | subagent из диспетчера | читать diff, `git diff/status/log` | править файлы, запускать тесты |

Правило: **один файл — один владелец**. Если задача требует чужой файл —
остановиться и вернуть её диспетчеру, а не лезть через забор.

## 2. Как запустить две рабочие сессии

Из корня репозитория (один раз):

```powershell
git worktree add C:\Users\starg\karta-web -b lane/web
git worktree add C:\Users\starg\karta-pipeline -b lane/pipeline
```

Дальше в OpenCode:

1. Открой новую сессию в `C:\Users\starg\karta-web`, выбери агента **web**.
2. Открой новую сессию в `C:\Users\starg\karta-pipeline`, выбери агента **pipeline**.
3. Главную сессию в корне оставь диспетчеру: он кидает задачи, проверяет
   diff, запускает тесты и мержит.

Максимум одновременно: **2 кодовые полосы + 1 исследователь**. Pipeline —
всегда одна полоса: PostGIS/Valhalla не любят двух одновременных импортов.

## 3. Карточка задачи (копировать в сессию)

```
Цель:
Разрешённые файлы/папки:
Не трогать:
Критерий приёмки (что увидит человек):
Как проверить (команда/URL/клики):
Данные: меняются / не меняются
Формула: меняется / не меняется
```

Без этой карточки агент не начинает. В конце — отчёт:

```
Изменено:
Проверено:
Числа до/после (если данные/формула):
Риски:
Что проверить руками:
```

## 4. Правила merge

- Агент коммитит и пушит **только свою ветку** (`lane/*` или `task/*`). Merge
  в `main` и деплой делает человек; PR открывает диспетчер.
- Перед merge: `git diff`, `git status`, тесты, сборка.
- Изменение формулы/данных — только с таблицей «до/после» по 10 домам.
- Конфликт в `config/scoring.json` или `web/public/data` — стоп, решает
  диспетчер.
- После merge worktree можно оставить для следующей задачи; ветку не удалять,
  пока не проверен деплой.

## 5. Онлайн-фабрика (без команды и бюджета)

С 19.11.2026 автономный цикл включён: `autopilot.yml` по push рабочей
ветки гоняет тесты, открывает PR, мержит его после зелёных тестов и
запускает `deploy.yml`; тот проверяет данные валидатором и публикует
сайт. Ручной approve деплоя снят по решению владельца.

Целевая схема — три слоя:

1. **Источники**: OSM (Geofabrik), data.mos.ru, ГИС ЖКХ, Мосэкомониторинг.
2. **Фабрика**: GitHub Actions.
   - `ci.yml` — тесты Python, `tsc`, `next build` на каждый push/PR.
   - `data.yml` — ручной/ежемесячный прогон: PostGIS-сервис, импорт,
     скоринг, экспорт; результат — zip-снимок в GitHub Release
     (`data-YYYY-MM-DD`) + `manifest.json` с датой, хешем и версией формулы.
   - `deploy.yml` — скачивает последний data-релиз, копирует в
     `web/public/data`, собирает и публикует сайт.
3. **Продукт**: статический сайт + `?building=` + позже `/r/<id>`.

Почему так:
- GitHub Actions снимает локальные проблемы: кириллица в пути, `ENAMETOOLONG`,
  ручной worktree, «собралось только на моём ноутбуке».
- Data-релиз даёт версионирование и откат: сайт всегда знает, на какой снимок
  данных он смотрит.
- Публичный репозиторий → бесплатные минуты CI; 27 МБ данных — нормальный
  размер релиза.

Порядок внедрения:
1. `ci.yml` — сейчас (тесты + сборка, без деплоя).
2. `data.yml` — сначала ручной прогон на Пресню, без Valhalla; маршруты
   остаются из текущего снимка, в отчёте честно писать метод.
3. `deploy.yml` — после того как data-релиз появится.
4. Valhalla в Actions — отдельная задача: кэш тайлов, только изменённые дома.
5. PMTiles и второй район — только после зелёного CI и data-релиза.

## 6. Что не делать

- Не запускать двух агентов в одной папке.
- Не давать агенту push в `main`/`gh-pages`, force-push и `npm run deploy`.
- Не генерировать 3 306 OG-страниц, пока карточка не проверена на реальных
  домах.
- Не добавлять платные API «на будущее».
- Не менять `scoring.json` без тестов и записи в `docs/decisions.md`.
