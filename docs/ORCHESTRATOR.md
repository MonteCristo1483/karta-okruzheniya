Дата: 2026-11-20. Инструкция для главной сессии-оркестратора. Его задача —
**не писать код**, а ставить задачи, проверять отчёты, держать STATE и
решения. Код делают отдельные сессии-исполнители.

## Цикл одной задачи

1. Оркестратор выбирает **одну** задачу и пишет бриф по шаблону ниже.
2. Пользователь открывает **новую сессию-исполнитель**, выбирает модель,
   вставляет бриф.
3. Исполнитель: ветка от `origin/main` → правки → `tsc`/`build` → push.
4. Autopilot: тесты → PR → merge → Deploy. Если упал — merge `origin/main`,
   разрешить конфликт, push. Не обходить тесты и не мержить руками.
5. Исполнитель присылает отчёт и 4 скриншота WebKit.
6. Оркестратор проверяет PR/Deploy/скриншоты: принять или дать короткую правку.
7. Значимое решение — строка в `docs/decisions.md`; состояние — `docs/STATE.md`.
   `decisions.md` только дописываем: старые строки не правим, исправление —
   новой строкой (иначе теряется история, как было 20.11).

## Визуальные задачи

Правила после промаха V1 (палитра ушла в «ночь»):

1. В брифе — **файл-ориентир** (`design/...png`) и конкретные целевые
   значения; «сделай красиво» не считается брифом.
2. Критерий проверяется **парой кадров**: обзор 15.35 и крупный план; плюс
   390 и тёмная тема. **Обязательно два DPR**: 1 (как у владельца на
   десктопе) и 2 (телефон). Скриншоты только в DPR 2 — недействительны:
   именно так мы три задачи смотрели «телефонную» картинку и не видели
   алиасинг на десктопе.
3. Хаб смотрит скриншоты **до** приёмки и сравнивает с макетом; при
   сомнении — второй взгляд через Gemini/Nemotron.
4. Промах по вкусу — не повод гонять ту же модель третий раз: меняем
   модель (Argon ↔ GPT-6 Luna), а не количество итераций.
5. Продуктовые цвета (шкала балла) не «оптимизируются» ради красоты:
   пять ступеней обязаны различаться на глаз.

## Ловушки

- **Все GitHub Actions — только по full-length SHA.** Тег `@v4` валит job на
  «Set up job» (`is not allowed ... must be pinned`), как случилось с
  `actions/cache` 20.11: два Deploy красных. При добавлении экшена сразу
  писать `uses: owner/action@<40 hex> # vN`.
- **Двойной мерж автопилотом.** Был: одна ветка мержилась дважды с пустым
  squash-коммитом. Закрыто guard'ом в `autopilot.yml` (проверка содержимого
  через `git merge-tree --write-tree`); three-dot diff не годится — после
  squash он продолжает показывать влитые изменения.
- **«Brief not found locally»** — worktree стоит на ветке прошлой задачи, а
  бриф новой появился в `main` позже; `git fetch` рабочие файлы не меняет.
  Лечится порядком: сначала `git switch -c task/<name> origin/main`, потом
  читать бриф. Если после переключения файла нет — писать в хаб, а не
  додумывать задачу по тексту промпта (так уже потеряли пункт «чипы 13px»).
- **Autopilot merge failure** чаще всего из-за отставшей ветки: сделать
  `git fetch origin`, `git merge origin/main`, разрешить конфликт в docs,
  push. Не мержить руками.
- **Сборка на кириллице** (`OneDrive\Документы`) падает; web собирать в
  `C:\Users\starg\karta-web`.
- **Локальный сервер** после проверки гасить; `.pages-test*` в git не тащить.
- **`web/AGENTS.md`** — генерируемый файл, не коммитить.
- **Прототипы** — локально, без push; сохранять в локальную ветку `proto/*`.
- **Данные** — только через ветку `data` (`data.zip`), не в `main`.
- **Секреты** — `MOSRU_API_KEY` только в локальном `.env`; в чат/репо нельзя.
